# Justfile Authoring

Use this skill to make a justfile discoverable (help, groups, documented arguments), keep its documentation from drifting, and keep credentials out of recipes' command lines. It works on any tech stack, on a new justfile or an existing one.

It does not teach `just` syntax. For that, run `just --man` or read the manual; `references/just-gotchas.md` lists only the traps that matter for discoverability.

## Prerequisites

- `just --version`. `[group]`, `[arg]` and `--explain` are recent; without them the `native` variant degrades to plain doc comments. Say so rather than assuming.
- **`native` needs only `just`.** For `rich` and `local-rich`, check `command -v justz && justz --version`. If it is missing or older than 0.5.1, tell the user how to install it (see the `justz-cli` skill) and stop. Never install it yourself, and never fall back to a hand-written help script.

## The three shapes

Choosing between them is the first real decision, not an implementation detail.

| | Where documentation lives | Cost |
|---|---|---|
| **`native`** (default) | `[doc]`, `[group]`, `[arg]` attributes in the justfile | Only `just`. No metadata file |
| **`rich`** | `commands.json`, next to the justfile, rendered and checked by `justz` | `justz` on every machine that renders help. Adds arg rows, examples, cross-references, formatting and CI checks |
| **`local-rich`** | A personal, git-ignored `.just-local-rich.json` generated by `justz generate` | `justz` for one developer. Nothing visible to the team |

`local-rich` is never part of the team question in step 2; it is a personal overlay (`references/variant-local-rich.md`).

Do not scaffold either shape before completing steps 1 and 2.

## Working procedure

### 1. Assess the repo, and print the assessment

Read before writing anything:

- The justfile and `just/*.just`: every recipe, its parameters, and what it runs underneath.
- Whether a help system exists: `config/commands.json`, `just/commands.json`, a `scripts/lib/help.sh`. If one does, this is an *improve* or *migrate* task: read `references/migration.md`.
- The tools a new contributor must install.
- Whether any recipe has a real flag surface, and whether a namespace carries a caveat that belongs to the namespace rather than to one recipe.

With `justz` installed, `justz assess --json` gives the exact counts (recipes, documented, modules, shebang and long recipes, registry coverage) and a recommended variant with its reason. Without it, count from `just --dump --dump-format json`. Then print a short factual assessment, the signals and not an essay. Format and thresholds: `references/choosing-a-variant.md`.

If a help system already exists, list what is *wrong* with it: a description that diverges between `commands.json` and `[doc]`, a guard that cannot fail, a public `default` recipe appearing as a row. `justz check` reports most of these.

### 2. Recommend a variant, then ask once

State the recommendation with its one-line reason and the one-line trade-off of each option, then point to `references/choosing-a-variant.md`. Do not paste the comparison.

Then ask **one batched question set** covering the variant and everything else that cannot be inferred, each with a recommended default:

| Decision | Why it cannot be inferred | Default to recommend |
|---|---|---|
| `native` or `rich` | A team preference and an ownership question | `native`, unless the repo clears every threshold in `references/choosing-a-variant.md` |
| Namespace taxonomy: group names and which recipe goes where | Highest-impact naming decision; a wrong guess costs a follow-up change | Your proposed 3 to 5 groups, derived from the actual recipes |
| Which recipes keep their bare top-level name | Renaming a daily command breaks muscle memory | Keep the 3 to 5 most-run recipes top-level under `core` |
| Migration for commands that move | Hard break or deprecation shims is a team cost decision | Document the moves in the README; add alias shims only on request |
| Latent bugs found while porting | Fixing silently hides them; porting silently preserves them | List them, fix them in the same change, call them out |
| Whether the check runs in CI | Depends on a CI system that may not exist | Wire it into `check`/`ci`; add a CI job only on request |

Ask before any file is created or moved. Script extraction is not on this list: it is a correctness default.

### 3. Scaffold

Read `references/shared-mechanics.md` (`mod` layout, argument shape, `set positional-arguments`, script extraction, `doctor`), then the chosen shape:

- **`native`**: `references/variant-native.md`.
- **`rich`**: `references/variant-rich.md`. The registry plus three recipes (`_default`, `help`, `check`) that call `justz`. No vendored scripts.
- **`local-rich`**: `references/variant-local-rich.md`.

### 4. Update the docs the team and agents actually read

Search the repository for documentation or agent instructions that still name raw tool commands (`make build`, `python -m pytest`, `npm run`) and replace them with their `just` equivalents: `README`, `AGENTS.md`, `.agents/skills/*/SKILL.md`.

Record **which shape the repo uses and why**, in one or two lines in `AGENTS.md`. Without it the next agent re-litigates the choice.

For agent-facing instructions in `AGENTS.md`, include a concise `## Running Tasks (just)` contract:

- **Discover from the CLI, never from `scripts/*/*.sh`**: `just` (summary), `just <ns>` (a namespace), and `justz help [group] <cmd>` (`rich`) or `just --explain <ns>::<cmd>` (`native`).
- **Pass flags directly, without `--`**: `just <ns> <cmd> -f val`.
- **Single-quote free-text arguments** containing `!`, `$`, `*` or spaces, so interactive Zsh history expansion and globbing never fail.

### 5. Verify

Find the justfile root with `just -c pwd`, not a hand-written parent walk: it follows `just`'s own lookup rules.

```bash
just                         # compact listing
just <ns>                    # one namespace
just <ns> <cmd>              # runs
just check                   # the documentation check (justz check in rich, the inline guard in native)
just --list                  # no orphaned recipe bodies, no `default` row
bash -n scripts/**/*.sh      # every script parses
shellcheck -S warning -x scripts/**/*.sh
(cd any/subdir && just <ns> <cmd>)   # repo-root paths still resolve
```

In `rich` repos also run `justz check` and `justz fmt --check`. Then add a deliberately undocumented recipe, confirm the check fails, and remove it. A guard nobody has seen fail is a guard nobody can trust.

## Avoid these mistakes

- Do not scaffold a shape before the assessment and the batched question. The choice is architectural and the user cannot answer it from a bare prompt.
- Do not paste the full comparison into the conversation. One line per option plus a pointer.
- Do not assume a tech stack: derive the tool list, description language and groupings from the repo's content.
- Do not decide the namespace taxonomy, the top-level command set or the migration strategy on the user's behalf.
- Do not silently fix, or silently carry over, bugs found while porting. Surface them and let the user choose.
- Before any edit the user has not explicitly requested (a taxonomy, a migration, a `local-rich` improvement pass), preview the concrete plan, recommend one option, then ask. Never pose an abstract yes/no with nothing to evaluate.
- Do not write a description that names the tool instead of the effect. `Type-check then bundle → dist/static/` beats `Build the project`.
- Do not create a public `default` recipe: it appears as a row in every listing. Use `_default`, first in the file.
- Do not declare a positional parameter ahead of a variadic; it swallows the first forwarded argument. Make it a flag.
- Do not author flags without short single-letter aliases (`-x, --long`) unless the flag name is already two letters (`--id`, `--ci`, `--ui`) or there is a collision. Do not alias two-letter parameters without asking.
- Do not use long flags in examples when short aliases exist.
- Do not write redundant examples: a bare command, or a single boolean flag the argument rows already show. `justz check` reports both.
- Do not leave `commands.json` unsorted. Run `justz fmt` after every edit; `justz check` rejects an unsorted registry.
- Do not vendor, copy or hand-edit a help script. `justz` renders the help; the registry carries `name`, `tagline` and `cli` if the defaults need overriding.
- When an `args` entry takes a bounded set of values, declare `"values": [...]` (it drives shell completion and renders as `(a|b|c)`) and show it in at least one group example.
- Do not interpolate a variadic (`for x in {{ args }}`) when the recipe parses or forwards it. Use `set positional-arguments` and iterate `"$@"`.
- Do not let a recipe consume the flags of a single tool it wraps. Detect and forward them so the tool keeps its own flag namespace.
- Do not add a per-recipe `-h`/`--help`. `just <ns>` and `justz help <ns> <cmd>` already render it.
- Do not leave multi-line shell in a recipe body. Extract it to `scripts/<ns>/<cmd>.sh` so it can be parsed, linted and run without `just`.
- Do not leave an orphaned indented block after a `#!/usr/bin/env bash` recipe: `just` silently absorbs it into the preceding recipe. Cross-check `just --list`.
- Do not render examples or footers with `printf` inside a recipe. A repo that wants structured examples wants `rich`.
- Do not duplicate a description. In `rich`, `commands.json` is authoritative and any `[doc]` must match it exactly (`justz check` enforces this); in `native`, `[doc]` is the only copy. Duplication produced a 20-of-32 divergence in the field.
- Do not tell agents to avoid `just --list` or `just --dump`. They cannot be stale; a registry can.
- Do not commit `.just-local-rich.json`, and do not scaffold it as part of the step 2 question. It is personal; `justz generate` refuses to write it where git tracks it.
- Do not put a secret value on a command line, in a justfile, or in a `commands.json` example. See `references/credentials-in-recipes.md`.

## Checklist

Both shapes:

- [ ] Prerequisites checked (`just --version`; `justz --version` for `rich`)
- [ ] Assessment printed: recipe and namespace counts, flag surfaces, cross-cutting caveats
- [ ] Existing help system detected and its defects listed, if there was one
- [ ] Shape recommended with a reason and confirmed in one batched question with the taxonomy and top-level set
- [ ] Every public recipe has a description; every top-level recipe has a group
- [ ] `_default` (private, first in the file) in the root justfile and in every submodule
- [ ] Documentation check wired into `check` and `ci`, and seen failing on a deliberately undocumented recipe
- [ ] No recipe declares a positional parameter before a variadic
- [ ] Modules whose recipes parse or forward arguments set `positional-arguments` and iterate `"$@"`
- [ ] Wrapper recipes forward the wrapped tool's flags rather than consuming them
- [ ] No recipe body holds multi-line shell
- [ ] `bash -n` and `shellcheck -S warning -x` pass for every script under `scripts/`
- [ ] `doctor` checks every required tool
- [ ] README and `AGENTS.md` updated, including which shape the repo uses and why
- [ ] `just`, `just <ns>`, `just <ns> <cmd>` verified, including from a subdirectory

`native` adds:

- [ ] `--unsorted` passed by the listing recipes, so source order survives
- [ ] `[arg(…, help='…')]` for every meaningful option, short form first where one exists
- [ ] `set unstable` + `set lists` scoped to only the modules that need boolean flags, with a comment saying why
- [ ] Mapped dependencies re-checked in any module using `set lists` (list values interpolate by concatenation)
- [ ] An `explain` recipe if any recipe uses a multiline `[doc]`

`rich` adds:

- [ ] `justz --version` is 0.5.1 or newer and the `help`, `check` recipes call it
- [ ] `justz fmt` run, and `justz fmt --check` plus `justz check` wired into `check`/`ci` and passing
- [ ] No `args` entry is a single catch-all placeholder; short aliases written `-x, --long <value>`
- [ ] Every bounded-value argument has `values` and an example that shows it
- [ ] `"cli"` set to the shim name if the project is wrapped by a shim
- [ ] Shim registered with `justz shim add` and completion installed with `justz completions`, if the team wants them
